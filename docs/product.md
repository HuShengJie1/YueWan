# 产品说明

## 产品目标

「约玩 / MeetUp Vote」把微信群中零散的讨论结构化，让朋友更快确定参与者、候选活动、可用时间和最终安排。它不替代聊天工具，而是承接“形成决定”这一步。

## 典型场景

一群朋友计划周末见面：有人分享餐厅，有人建议密室或桌游，每个人空闲时间不同。发起人创建群组和一场约玩局，成员提交候选活动、表达活动态度、勾选多个可用时间，系统汇总后确认正式活动。

## 核心概念

- **User**：未来通过微信登录的用户。
- **Group / GroupMember**：朋友群组及成员关系，一个用户可加入多个群组。
- **Poll / Hangout**：属于某个群组的一次约玩决策，未来状态为 `draft`、`voting`、`confirmed`、`cancelled` 或 `finished`。
- **Proposal**：成员提交的候选活动，可带通用的外部平台、URL 和元数据。
- **ProposalVote**：对候选活动表达 `LIKE`、`OK` 或 `DISLIKE`，不是二元投票。
- **TimeOption / TimeVote**：明确的候选时间，以及成员可多选的可用时间。
- **Event**：约玩局确认后形成的正式活动。

## 未来业务流程

```text
创建或加入群组
→ 发起约玩局
→ 添加候选活动与明确时间
→ 活动投票与时间多选
→ 汇总结果
→ 确认正式活动
```

## MVP 范围

MVP 包括：用户、群组、加入群组、创建约玩局、候选活动、活动投票、时间投票、最终结果和确认活动。

MVP 暂不包括：聊天、AA 付款、AI 推荐、活动照片、好友系统、商业化，以及大众点评等平台的深度 API 集成。

当前已实现微信登录与用户资料、群组与成员、约玩局草稿，以及候选活动和候选时间的创建、分页、编辑、删除闭环。约玩局及候选只对 active 群组成员可见；候选只在 `draft` 阶段可写，并由候选创建者、约玩局创建者或群主管理。

已实现约玩局从 `draft` 开启 `voting`、活动的 `LIKE/OK/DISLIKE` 互斥投票、时间多选原子替换和实时聚合摘要；只有 active 成员可读可投，进入 `voting` 后候选锁定为只读。小程序详情页已接入开启投票、活动选择与撤销、时间多选保存、实时票数和截止后禁用。

后端已实现 MVP 手动确认闭环：投票摘要只提供参考，不自动计算获胜者；约玩局创建者或 active 群主从同一 Hangout 手动选择一个 Proposal 和一个 TimeOption，生成保存候选快照的 Event，并原子切换到 `confirmed`。确认可在截止前提前进行；成功后投票摘要仍可读，但不能继续写票。同一 Hangout 的相同选择重复确认幂等，不同选择安全冲突。小程序尚未接入确认和 Event 展示；`cancelled/finished` 流转、参与者 RSVP 和第三方平台解析仍未实现。
